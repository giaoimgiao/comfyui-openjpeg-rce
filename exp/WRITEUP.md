# 从一张 J2K 图片到 root：Pillow 内嵌 openjpeg 越界写的完整利用链

> **状态**：本地 PoC（在作者环境复现成功，见 `exp/`）。
> **披露状态**：目标为 Pillow 12.3.0 内 **vendored** 的 openjpeg 2.5.4（补丁未跟进）。
> **在完成协调披露前，请勿公开投递细节。** 本文为技术记录草稿。

---

## 0. TL;DR

- **入口**：一个 J2K(JPEG2000) 文件。
- **根因**：openjpeg `j2k.c` 的 `read_sod()` 按 **TLM 声明的 tile-part 数** 分配
  `tp_index` 数组，却按 **SOT 的 `TPsot`** 递增写入 ⇒ 越界写（OOB write）。
- **原语**：每个越界 part 连续写两个 8 字节值（`v1`=SOD 文件偏移，`v2`=下一 part 偏移−10），
  构成一个"地址单调递增的规律双写"。
- **利用（Data-Oriented，不用 free/UAF/GOT/ROP）**：
  1. 用 **3 段**越界写把紧邻 `tp_index` 的、**我们自己伪造的大 `bytes`** 改造成 `memoryview`
     （`ob_type→PyMemoryView_Type`，`view.buf→任意地址`）；
     之后 `victim[i]` / `victim[i]=x` 就是**任意内存读写**。
  2. 两次解码：① `buf`=目标 `str` 地址 → 把命令写进它的首字节；② `buf`=`PyUnicode_Type.tp_repr` → 写入 `system`。
  3. `repr(str)` ⇒ `system("id")` ⇒ 命令执行（本环境 `uid=0(root)`）。

## 2. 漏洞根因（源码级）

`openjpeg/src/lib/openjp2/j2k.c`：

```c
/* read_sot()：数组大小 = TLM 声明的条目数 */
if (! p_j2k->...m_tlm.m_is_invalid) {
    /* do nothing */
} else { /* 只有 TLM 无效时才扩容 */ }

/* read_sod()：写索引来自 SOT 的 TPsot */
OPJ_UINT32 l_current_tile_part =
    cstr_index->tile_index[tile].current_tpsno;      /* 由 TPsot 递增 */

l_cstr_index->tile_index[tile].tp_index[l_current_tile_part].end_header = l_current_pos;
l_cstr_index->tile_index[tile].tp_index[l_current_tile_part].end_pos    =
        l_current_pos + sot_length + 2;
```

**TLM 有效时数组永不增长**，而 `TPsot` 可以一直增：
当 `TPsot >= TLM条目数` 时，下标越界 ⇒ 在 `tp_index` 数组之后连续写两个 8 字节。
（对应 OSV-2025-219 / PR#9520 一类 J2K 越界写。）

## 3. 原语的精确刻画

设数组基址为 `tp`，第 `k` 个越界 part（`k = TPsot = N, N+1, ...`，`N` 为 TLM 条目数）写入：

```
写点：tp + 24N + 8·...      相对"数组后第一个对象"(victim) 的偏移：
  k = N   →  victim+0x00 (v1) , victim+0x08 (v2)
  k = N+1 →  victim+0x18 (v1) , victim+0x20 (v2)
  k = N+2 →  victim+0x30 (v1) , victim+0x38 (v2)
```

- **自由槽**（值可控）= 偏移 ≡ 8 (mod 24)：`+0x08 +0x20 +0x38 +0x50 ...`
- **耦合死槽**（值 = 前一个自由槽 + 2）= 偏移 ≡ 0 (mod 24)：`+0x00 +0x18 +0x30 +0x48 +0x60 ...`
- **单调约束**：`v2(k) = (part k+1 的 SOD 偏移) − 10`，part 在文件里顺序排列
  ⇒ **地址越高的槽，值必然越大** ⇒ `+0x08 < +0x18 < +0x20 < +0x30 < +0x38 < ...`

### 3.1 单调约束的直接结论
`ob_type(+0x08) < buf(+0x38)`。由于 `PyMemoryView_Type = 0xa350c8` 高于所有
GOT 槽（`0xa1ffe8–0xa21020`）⇒ **GOT 覆盖不可达**，必须换靶子。

## 4. 利用思路：Data-Oriented（把对象"嫁接"成 memoryview）

> 关键转变：不要去找"哪个对象会被释放"（那只能靠扫），而是问
> **"我要让哪个合法操作替我去读写内存"**。

`memoryview` 的 `Py_buffer` 结构（CPython 3.12）：

```
+0x38 view.buf    ← 数据指针（自由槽 ✓）
+0x40 view.obj    +0x48 view.len
+0x50 view.itemsize   +0x58 readonly(int)/ndim(int)
+0x60 view.format     +0x68 view.shape    +0x70 view.strides
```

只要把 `view.buf` 指向任意地址，`mv[i]` / `mv[i]=x` 就是任意读写，**解释器正常逻辑**。

### 4.1 三个工程约束（全部踩过）
1. **只写到 stride `m=2`（`+0x30/+0x38`）就停**。
   若继续写 `m=3`，则耦合规则强制 `view.format(+0x60) = itemsize(+0x50) + 2`，
   无法同时满足 `itemsize=1` 且 `format` 合法 ⇒ `mv[0]` 崩。
2. **`N` 必须为奇数**。victim 基址 `= 24N+8` 必须等于 `tp_index` 的 chunk size
   `align(24N+8,16)`；否则错位 8 字节，会把写打进邻居的 **chunk size 字段** ⇒
   `double free / corrupted size`。本例取 **`N=23`**（chunk `0x230`）。
3. **victim 必须 >512 字节**（走 glibc 堆）。
   Python 小对象（≤512B）走 **pymalloc**，与 `tp_index`（glibc malloc）**永远不相邻**。

### 4.2 受害者：一个大 `bytes`，内容里预置 view 结构
victim = `bytes(608)`，其内容从 `obj+0x20` 起，因此把 view 字段直接写进内容：
`format` 指向 `'B'`、`shape`/`strides` 借用临时 memoryview 的地址。
经 3 段越界写后，它就"变成"了一个可用的 memoryview。

### 4.3 堆风水（布置，而非扫描）
```
drain 旧空闲块(hold) → 连续分配 400 组 [D(bytes519,chunk0x230)] [victim(chunk0x290)]
→ 只释放"对齐"的 D（id(v)-id(D)==0x230）→ 解码
⇒ tp_index(N=23, chunk0x230) 落进洞，其邻居正好是 victim
```

## 5. 从任意读写到 RCE

由于 `buf ≥ 0xa350c8`（单调约束），可达靶子为 **类型对象的 `tp_*` 槽**：

```
buffer = PyUnicode_Type.tp_repr (0xa3c908)
mv[0..7] = &system                ⇒  repr() 变成 system()
```
再把一个大 `str` 的首 8 字节写成命令，`repr(str)` ⇒ `system(str_ptr)` ⇒ 执行。

**细节**：`repr(x)` 会 `LOAD_GLOBAL` 一次 ⇒ 对象 `ob_refcnt`（即内存首字节）**+1**，
所以首字节写 `'h'`，执行时正好是 `'i'`（命令 `id`）。

## 7. 影响面与限制（诚实版）

| 项 | 说明 |
|---|---|
| **前提 A：文件可到 ~11–13MB** | 值即文件偏移，而目标地址 ≈ `0xa2–0xd0`（10.6–13MB）⇒ 文件必须 > 该值。**≤10MiB 上传限制的部署天然不受影响**。 |
| **前提 B：地址稳定** | 本次利用使用固定绝对地址（本环境 Python 基址 `0x400000` 固定、无 ASLR）。带 ASLR 的部署需要先做信息泄露。 |
| **前提 C：堆风水可重复** | 依赖 glibc 分配行为；不同版本/负载下需要重调 chunk 档位与 `N`。 |
| **崩溃风险** | 未命中的解码会破坏堆（DoS）。 |

## 10. 方法论：给"写 N 字节"原语先定性（本文最重要的可复用经验）

任何"能写入 N 个受控字节"的原语，**第一步不是找受害者对象，而是给值的语义定性**——
即：这 N 字节在**消费端**会被当作什么来用？

| 语义类型 | 消费端把它当 | 可用性取决于 | 例子（本链） |
|---|---|---|---|
| **地址型** | 指针（解引用） | **内存布局**：必须是合法映射地址 ⇒ 受 ASLR/PIE、值域（文件大小）、单调/顺序约束 | `ob_type`、`view.buf`、`tp_dealloc` 槽 |
| **长度/计数型** | `len` / `size` / `index` / `count` | **只需数值可表达**（几乎不受布局约束） | `view.len`、`ob_size`、`ob_alloc` |
| **类型/标签型** | 类型指针 | 需要合法对象地址，但**候选集合很大**（所有类型对象） | `PyMemoryView_Type` 等 |
| **标志型** | bool / 位域 | 只需 0 / 1 | `readonly`、`ndim`、`is_invalid` |

### 10.1 本链的教训（我们**判错了语义**）

原语写入的两个槽满足：

```
自由槽 f 的值 = V      ⇒      死槽 (f+0x10) 被迫 = V + 2
（例：buf(+0x38)=V  ⇒  len(+0x48)=V+2）
```

- 当成**地址型**看：这个耦合是**灾难** —— `itemsize`/`format` 无法同时合法，
  `list.ob_item`/`bytearray.ob_start`（都在死槽）永远够不到，GOT 也够不到。
  我们为此耗掉了绝大部分时间。
- 当成**长度型**看：同一个耦合是**白送** —— `len = V + 2` 天生是个"巨大但无害"的数。
  令 `buf = 0xb00000`（堆基址，仍满足 `> 0xa350c8` 的单调约束），
  则 `len ≈ 11MB` ⇒ **`mv[: N]` 就是一次覆盖整个 glibc 堆的越界读**。

### 10.2 由此得到的通用推进顺序（可套用到其它"写 N 字节"漏洞）

```
① 定性：列出所有"落在可写偏移上的字段"，按上表分类
② 优先吃"长度型"：
   · 长度型 = 数值可表达 ⇒ 不受 ASLR 约束 ⇒ 先拿【越界读 / 信息泄露】
   · 泄露到手 ⇒ ASLR 被打掉 ⇒ 之后所有"地址型"操作才变得可靠
③ 再吃"类型/标签型"：候选集合大（所有类型对象都在值域内）
④ 最后才吃"地址型"：此时地址已知（② 的泄露），布局约束已被消解
⑤ 全程优先选【目标程序自己会去使用的对象】⇒ 把"我们驱动的利用"
   变成"程序自己驱动的利用"（= 远程、无需执行点）
```

### 10.3 反面教材（本文档自己的历史）

早期我们把 90% 时间花在"地址型"路线上：找一个会被释放的受害者 ⇒ 让 dealloc 去 `free(可控地址)`。
那条路每一步都被"地址型"约束锁死（值必须 ≥0xa350c8、必须单调、GOT 不可达、受害者不释放）。
**根因不是技术不够，是语义判错。**

### 10.4 本轮实验状态（诚实记录）

- `leak2.py`（沿用 exp.py 已验证时序，仅把 stage1 的 C 换成堆基址）实测：
```
  mv1 buf=0xb00000      <- 指针字段嫁接成功 OK
  itemize=0x1  len=0x10  <- len 没变（仍是我们模板预置的 16）NG
```
- **原因不是调参，是结构性的**（见 §11）：`len` 在 +0x48，要写它就必须多写第 4 对
  {+0x48,+0x50}，而那对会耦合强制 `format(+0x60)=itemsize(+0x50)+2` 杀 `format`。
  ⇒ **"大 len" 与 "活 format" 在本网格上不可兼得。**
- 这一结果反过来验证了 §11 的规则：**网格先天地筛掉了某些语义类别**。

## 11. 由"语义定性"推出的新规则：步长决定的语义可达性

### 11.1 实验（leak2.py）
想用"长度型"红利（`buf=堆基址` ⇒ 期望 `len=buf+2` 巨大）：

```
  buf = 0xb00000      OK   (指针字段嫁接生效)
  len = 0x10          NG   (仍为模板预置值；耦合写入没有发生)
```

**为什么**：耦合只发生在**同一个写对内部**（`(24k+8, 24k+16)`）：

```
 第1对 {+0x00,+0x08}  第2对 {+0x18,+0x20}  第3对 {+0x30,+0x38}   <- 我们用了这三对
 len 在 +0x48  => 必须用第4对 {+0x48,+0x50}
 而第4对会把 itemsize(+0x50) 一起写掉 => 耦合强制 format(+0x60)=itemsize+2 杀 format
 => 「大 len」与「活 format」不可兼得（结构性，不是调参）
```

### 11.2 通用规则

> **写原语的偏移网格（由 stride / 写入槽决定）先天地决定了你能使用哪一类语义。**
> 应当**从网格反推可用语义**，而不是先挑语义再撞网格。

本链网格（stride 24、两槽 +8/+16）相对受害对象的可达偏移：

```
可达  : +0x00 +0x08 +0x18 +0x20 +0x30 +0x38 +0x48 +0x50 +0x60 +0x68 ...
不可达: +0x10 +0x28 +0x40 +0x58 ...            (≡ 16 mod 24)
```

与 CPython 字段布局求交，直接得到**能力表**：

| 语义类别 | 依赖字段 | 本链可达 | 状态 |
|---|---|---|---|
| 类型 / 标签型 | `ob_type` @+0x08 | **YES** | **已打通**（memoryview 嫁接 → 任意读写） |
| 指针型（自由槽） | `view.buf` @+0x38 | **YES** | 已打通（buf 精确可控） |
| 标志 / 小长度型 | `itemsize` @+0x50 | YES | 已打通（**继承**模板的 `itemsize=1`，不写它） |
| **大长度型** | `ob_size` @+0x10 | NO | `bytes`/`str`/`list`/`bytearray` 的长度**全部不可达** |
| 大长度型（替补位） | `view.len` @+0x48 | 半 | 能写但**必杀 format** ⇒ 结构性不可用 |
| 掩码 / 计数型 | `set.mask` @+0x20、`list.allocated` @+0x20 | **YES** | 待验证（下一批候选） |

### 11.3 完整评估流程（§10 + §11 合起来）

```
(1) 由 stride / 写入槽推出【可达偏移集合】
(2) 与目标解释器/程序的【字段布局表】求交
(3) 交集中每个字段标上语义类别（地址/长度/标签/标志）
(4) 按 §10.2 优先级挑（长度型 -> 标签型 -> 地址型），且优先挑【目标程序自己会用的对象】
(5) 不可达不等于放弃：换"语义等价的位置"
    （长度不可达 -> 找掩码/计数型；指针不可达 -> 换 type 槽）
```

### 11.4 本链由此选出的下一步

| 目标 | 位置 | 为什么它能做功 |
|---|---|---|
| `set.mask` | +0x20（自由槽） | 掩码是**纯数值**，可以是任何数（**不必是合法地址**）⇒ 不受 ASLR 约束；可控探针下标 ⇒ 天然的越界读写入口 |
| `list.allocated` / `array.allocated` | +0x20（自由槽） | 容量语义；配合 append 类操作可越界写 |
| 服务器自己的输出路径 | — | 类型型已打通 + 服务器序列化 ⇒ **盲泄露**，完全不依赖长度字段 |

## 13. 第二道过滤器：对象放置（pymalloc vs glibc）

§11 只考虑了"偏移网格"。实际还有一道**前置过滤**：受害者对象必须先能**坐在数组后面**。

```
CPython 分配器分工：
  ≤ 512B 的对象      -> pymalloc（自己的 arena，地址形如 0x7x...）
  > 512B 的对象/裸内存 -> glibc malloc（地址形如 0xb0...~0x110...）
tp_index 由 openjpeg 用 opj_calloc -> glibc malloc
=> 只有【glibc 堆】上的对象才可能成为它的邻居
```

### 13.1 实测（layout_pipeline.py）
```
大 bytes(1024)    id=0xc39b10   glibc  OK 可当邻居
大 tuple(80)      id=0xbc4700   glibc  OK 可当邻居（items 是指针）
bytearray 缓冲      0xc734e0     glibc（但对象本体小 => 本体在 pymalloc）
bytearray 本体     0x737ee...    pymalloc  NG
set / list / dict 本体  <=512B    pymalloc  NG
```

### 13.2 两道过滤器的交集 == 能力真相

> **大长度型语义在"服务器自己的对象"上不可达。**
> - 所有容器的长度都在 `+0x10`（≡16 mod 24，网格外）
> - `memoryview.view.len` 在 `+0x48`（能写，但耦合必杀 `format`）
>
> => "用长度把服务器内存读出来"这条路在本漏洞下**结构上不存在**。

可用的只剩两类（均已在本链打通）：

| 类别 | 前提 | 状态 |
|---|---|---|
| 类型/标签型 | 目标对象须在 glibc 堆 | ✅（memoryview 嫁接） |
| 指针型（自由槽） | 同上 | ✅（buf 精确可控） |

### 13.3 “服务器侧对象”靶子的正确形状

```
PIL 的 C 扩展自己用 malloc 分配的结构（Imaging / ImagingMemory ...）：
  ✓ 与 tp_index 同堆（glibc）
  ✓ 在【解码期间】被创建 => 与 tp_index 同一时间窗
  ✓ 内容全是【函数指针 + 内存指针】
```

这正是 §27 里反复落进写窗口的那批"带函数指针的结构体"邻居
（当时记下了 `0x524c14` / `0x5083a0` / `0x4c9b90` 却把它们当障碍）。
**它们不是障碍，它们就是"服务器自己会用的对象"本身。**

### 13.4 下一步实验（已定）

```
1. 把 §27 的那批邻居结构识别出来：是 PIL 的还是 CPython 的（符号/偏移比对）
2. 看其中哪个字段，在解码/编码后续流程中会被【解引用】或【被调用】
3. 用已打通的【指针型】写入把它指向我们的数据/函数
   => 触发者变成“服务器自己的后续操作” => 无需执行点的远程利用
```

## 14. 第三道过滤器：值的可表达性（三层模型完成）

### 14.1 新证据：邻居是 CPython 堆对象，不是 PIL 的 C 结构

把 §27 落在写窗口里的那些指针用 objdump 标签反查：

```
0x5083a0  ->  PyObject_SelfIter@@Base        <- 典型 tp_iter 槽的值
0x524c14  ->  PyType_GetModuleByDef@@Base+0x274
0x4c9b90  ->  _PyCode_CheckLineNumber@@Base+0x4bc
0x50b420  ->  PyObject_Free@@Base
```

=> 邻居是**堆上的 CPython 对象（很可能是堆类型对象 PyTypeObject）**，
   即“带函数指针的表”= 天然的 call-hijack 靶子。

### 14.2 但第三道过滤器挡在中间

```
原语写入的值 == 文件偏移
  => 值域 = [0x70, 文件大小]
  => 一切 >文件大小的值都写不出来
```

后果非常明确：

| 想做的事 | 需要写的值 | 可否表达 |
|---|---|---|
| `tp_repr` 指向 `system`（libc 0x7f...） | libc 地址 | **NO**（文件不可能有 0x7f00000000000 字节） |
| `tp_repr` 指向 python3.12 内的某个函数 | 0x4xxxxx | **YES** |
| `view.buf` 指向堆内对象 | 0xb0..~0x11x | YES |
| 指向 .data 里的类型对象 | 0xa21..0xa40 | YES |
| **任何长度/尺寸字段** | 小整数 | 可表达，但**网格不可达**（§11）|

### 14.3 三层过滤器 = 完整的能力边界

> **①偏移网格** 决定“哪些字段可达”（≡{0,8} mod 24）
> **②对象放置** 决定“哪些对象能当邻居”（glibc 堆、≥512B，或在解码中新建）
> **③值可表达性** 决定“能写入什么数”（≤ 文件大小）

三者交集给出本漏洞的**真实天花板**：

```
可以：把某个字段改成【文件内可表达的任意数】——即任意小地址/偏移/小整数
不可以：写一个 libc/栈地址；不可以写任何长度字段（网格外）
```

**这就精确解释了整条链的形状**：
- 本地 RCE 之所以成立，是因为中间加了“嫁接 memoryview”这一跳：
  用【原语】把 `buf` 设成一个可表达地址 ⇒ **升级出了不受过滤器③约束的任意写**（`mv[i]=x` 可写任意字节，包括 libc 地址）✓
- 纯盲打远程 RCE 之所以没组成，是因为升级后仍受 ①② 约束：
  被嫁接的对象必须是**我们能拿到的**那个；而“服务器自己会用的对象”要同时满足① ②，且要能让服务器对它做 `obj[i]`/`len(obj)`。

### 14.4 由三层模型推出的“缺失一跳”设计（构造，而非扫描）

关键事实：**Pillow 解码大文件时是按块（MAXBLOCK=65536）读入的**。

```
时间线：
  T0  open()                —— 输入缓冲在【数组之前】=> 不能当邻居 NG
  T1  read_tlm/read_sot -> calloc(tp_index)      <- 我们的数组在这里
  T2  read_sod 写入越界（可控制发生在第几个 part）  <- 我们的写在这里
  T3  Pillow 继续读后续块 => 【在数组之后】分配新的 bytes 块缓冲  <- 可当邻居 YES
```

=> **把 OOB 触发时机（第几个 part）往后拖，就能命中 T3 之后新分配的那个块缓冲**；
   再把它的 `ob_type` 改成 `memoryview`、`buf` 指向我们想读的内存 ⇒
   **解码器自己会按“我们指定的地址”去取码流数据** ⇒ 等价于服务器自己把内存读进
   解码结果 ⇒ **盲泄露（图片里带回服务器内存）** ⇒ 无需执行点。

### 14.5 本轮结论（诚实）

- 三层过滤器是**本轮最有价值的产出**：它把“为什么这条链只能做到本地 RCE”从模糊感受
  变成了可证伪的三条约束。
- 纯远程盲打 RCE 在本漏洞上**未打通**；但 14.4 给出了有依据的构造路线
  （时序对齐 + 块缓冲当邻居），这是“设计”而不是“扫描”。
- 已交付且可复现的部分见 §6（本地 RCE）与 deliver/（DoS + 检测器）。

## 17. 2026-10-10 第十三轮：远程"服务器驱动"的**实测否决**（含前置条件）

### 17.1 本轮三个独立测量

=> **窗口内能碰到的东西对解码流程没有任何影响**（惰性元数据）
**(C) "上传文件本身的 bytes" 能否当受害者：**
```
文件必须 >= 11~15MB（值即文件偏移）   而 glibc mmap 阈值默认 128KB
=> 实测 data（上传 bytes）落在 mmap 高地址 0x7aec557010  => 不在 brk 堆 => 不可能当邻居 ✗
（要让它走 brk 堆就要把文件压到 <=128KB，而那又写不出 >=10.6MB 的值 ⇒ 直接矛盾 ✗）
```

### 17.2 远程一跳的**前置条件**（可操作的结论）
要拿到"服务器自己会用的对象"，必须同时满足：
```
(1) 该对象在【解码之前】已存在（否则它在数组之后且距离 >6KB ✗）
(2) 尺寸在 512B .. 128KB 之间（<512B 走 pymalloc 不可能相邻；>128KB 走 mmap 不可能相邻）
(3) 它是 glibc(brk) 堆对象，且在堆上位于数组空洞之后（可由 groom 决定）
(4) 管线在解码【之后】还会使用它（= 才能形成"服务器驱动"）
```
**=> 红队可操作形态：** 在目标管线里找"跨解码存活、且尺寸 512B~128KB、且解码后还会被读/写的 bytes/bytearray 缓冲"。
典型例如：任务里携带的第二个小图（512B~128KB）、缓存中的元数据缓冲、缩略图缓冲等。
满足以上 4 条时，本链的"类型混淆 → memoryview → 服务器自己读/写"即可成立。

## 18. 🎉 2026-10-10 第廿轮：**服务器驱动写（解码器自己写进我们指定地址）—— 成立**

### 18.1 实测输出（fake_tc.py，官方有洞库）
```
[*] SCRATCH=0xd32d70  FAKE=0xc242d0  RES=0xdbb010
[*] A=0xc242c4 B=0xc252c4 C=0xc282c4
[*] 相邻对 = 387
[*] 解码成功: (16, 16) L                              <- 解码本身成功

[+] 非哨兵字节数 = 256                                <- 16x16 个 int32 = 正好是解码输出
★★★ 服务器驱动写成立：解码器把数据写进了【我们指定的地址】
```
（结尾的 double free 是收尾清理产物，写入与解码都已完成。）

### 18.2 完整链（本回合打通）
```
1. 越界写窗口 tp_index+0x230..：正下方就是 opj_tcd_tile_t（tiles[]）
2. 实测映射：tile->comps(+0x18) == A + 0x0c    （A = 构造器传入的第一个值）
   => 令 A = FAKE - 0x0c ，即把 comps 指向我们伪造的 tilecomp
3. 伪造的 opj_tcd_tilecomp_t（建在我们自己 >=512B 的 bytearray 里，地址低、可表达）：
     +0x10 numresolutions = 1
     +0x14/+0x18 compno/min_num_res = 1
     +0x20 resolutions -> 伪造的 40 字节零结构（numbands=0 => 不进 cblk 循环）
     +0x30 data         -> 我们指定的地址（SCRATCH）
     +0x38 ownsData     = 0（不让它 free 我们的地址）
     +0x48 data_size    = 4096
4. 解码器【自己】把解码像素（16x16x4B = 256B）写进 SCRATCH
   => 攻击者可控内容（像素来自我们上传的图）+ 攻击者可控地址（值可表达即可）
```

### 18.3 意义
- **上传一个文件，服务器自己往我们指定的地址写我们指定的内容** —— 不需要目标机上的执行点。
- `data` 指向服务器内存并让结果回传 = **盲泄露**；指向 .data 类型槽/堆对象 = **受控写 ⇒ RCE 侧**。
- 与 §17 的区别：§17 要找"旁观者对象"且被分配器挡；这里直接劫持**解码器自己的结构体指针**，避开分配器。

### 18.4 工程要点（本轮新增，全部实测）
```
· 受害者必须与数组【同档】：bytes(519) => chunk 0x230（不同档时相邻对 0/600；同档 584/600）
· bytes(x) 对 bytes 输入【不新建对象】=> 必须 bytes(bytearray(x))
· 自验证配对喷射：[D=bytes519][B] + 运行时校验 id(B)-id(D)==0x230
· 只释放【一个】洞：多洞会让窗口打到 free chunk header => 崩
· 伪造结构所在的 bytearray 必须 >=512B（<512B 走 pymalloc => 高地址 => 值不可表达）
· 映射关系：comps = A + 0x0c（A 为构造器第一个值）；tile 正下方 0x230
```

### 18.5 已知残留
- 收尾阶段 double free（伪造结构被库清理路径碰到）；不影响解码与写入，属可用性完善项。
- 地址仍依赖本机固定基址（无 ASLR）；远程需配合信息泄露（下一步）。

## 23. 2026-10-10 第廿五轮：赌信息泄露（战略可行，harness 卫生仍是拦路虎）

### 23.1 ★ 关键战略结论（这一轮最值钱的东西）
```
越界写写的是【完整的 8 字节值】，而值 = 文件偏移（可自由选择到 ≤ 文件大小）
=> 只要文件够大（本例 >10.7MB），【任意 ≤ 文件大小的地址】都能被“表达”
=> 于是：把 +0x08 写成 0xa350c8 (PyMemoryView_Type)
        把 +0x38 写成 0xa500d0 (要读的地址, 内容是真实代码指针 0x46ef54)
        把 +0x48 被耦合成 buf+2（巨大 len，正好用来跨堆读）
   => 活 bytes 对象变 memoryview，buf 指向 .data
   => v[:64].tobytes() 读出代码指针 => 打掉 ASLR
⇒ 即：信息泄露【不需要】伪造树、不需要多段拼装，用现成的越界写就能做到
   （A/B/C 三个值 <B<C 的顺序也满足：0xa350c8 < 0xa40000 < 0xa500d0）
```

### 23.2 实施状态

```
· PyMemoryView_Type / 读取地址 / 受害者内容预置（view.obj=合法对象, ndim=1）都已就位
```
